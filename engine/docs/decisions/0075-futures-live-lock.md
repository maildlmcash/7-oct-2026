# 0075 — Live futures lock

Status: accepted for a fail-closed live futures lock. Separate human approval and a passed release gate change the reason. They do not enable live mode. Live orders stay locked.

## Context

TASK 15.C.02 asks for configuration and API checks that reject live futures credentials and orders until separate human approval and release gates are recorded. Tests must prove that a UI-only change or an environment default cannot enable live mode.

Design page 2 keeps live order paths locked until paper and shadow gates, risk controls, reconciliation, and explicit two-person approval pass. Design page 13 separates baseline product acceptance from permission to trade live funds. Design page 16 keeps live OFF until distinct approvals are recorded. It does not name an approval signature, a 28-day count, or a 200-outcome count. Decision 0019 records the release gate and does not read live trading flags. Decision 0064 does not read `LIVE_TRADING` or `LIVE_ORDERS_LOCKED` from the environment. Decision 0074 drills futures failures and does not unlock live orders.

The canonical health object is `apps/web/health.mjs`. The canonical release gate is `services/release-gate.mjs`. The editor gate is `canEditChecklist`. Distinct-approver phrases are reused from the futures review. No live futures order route exists. The API check is `checkLiveFutures`. Session, checklist-owner, and view-state routes were not changed.

## Decision

`services/futures-live-lock.mjs` exports `createLiveFuturesLock`, `recordLiveFuturesApproval`, `checkLiveFutures`, and `FUTURES_LIVE_LOCK_LIMITATIONS`.

`checkLiveFutures` copies `liveTrading` and `liveOrdersLocked` from the frozen health object. `configSource` stays `health`. `environmentHonored` stays false. `liveEnabled` stays false. `liveOrderSubmitted` stays false. `venueClient` stays null. `credentialStored` stays false. The module does not read environment variables. A caller environment object and the UI fields `liveTrading` and `liveOrdersLocked` are not the switch. An omitted environment stays `OFF` and locked. A supplied environment that matches `OFF` and true is still not honored. A supplied enable value returns `live mode cannot be enabled` on a configuration check and is not echoed.

An order or credential check requires two distinct same-tenant Admin approvals and the latest same-tenant `release-gate` audit. That audit must have result `passed`, reason `release gate passed`, `edited` false, and `deployed` false. Zero approvals return `human approval is not recorded`. One approver returns `human approval is not separate`. A repeated approver id returns `approvers are not distinct`. The requesting Admin cannot be an approver (`maker cannot approve`). The same Admin and the same `changedAt` replay the approval. A different `changedAt`, or a third Admin, returns `approval is already recorded`. A missing audit returns `release gate is not recorded`. Any other latest audit returns `release gate is blocked`. A later blocked audit relocks the reason. Both records present still return `live orders are locked` or `live credentials are not allowed`. Nothing is submitted and no credential is stored.

A Spot product is `product is not supported` and is not stored. A Customer or a cross-tenant Admin writes no approval. Credential fields are not stored and are not echoed. The check does not append a release audit, does not call a paper order, and does not call the pre-trade gate. No PostgreSQL table was added. `health.mjs`, `release-gate.mjs`, `session.mjs`, and `futures-drills.mjs` were not changed. No HTTP route was added.

## Evidence

`pnpm test:futures-live-lock` passed 3/3, duration_ms 314.254208. A configuration check with no environment returns `liveTrading` `OFF`, `liveOrdersLocked` true, `liveEnabled` false, and `environmentHonored` false. The same flags hold when the caller environment matches `OFF` and true. Setting the process environment to an enable pair outside the module leaves the check `OFF` and locked. A caller environment or UI pair that asks to enable returns `live mode cannot be enabled` and does not echo `ON`. Zero approvals return `human approval is not recorded`. One approver returns `human approval is not separate`. The same Admin and `changedAt` replay. A different `changedAt` returns `approval is already recorded`. A third Admin returns `approval is already recorded`. The requester as an approver returns `maker cannot approve`. A duplicated approver id returns `approvers are not distinct`. No audit, and another tenant's audit, return `release gate is not recorded`. A blocked audit and an edited passed audit return `release gate is blocked`. Two distinct approvals and a passed release gate still return `live orders are locked`, with `releaseRecorded` true, `liveOrderSubmitted` false, and `venueClient` null. `fixture-credential` returns `live credentials are not allowed` and is not stored. An `apiKey` returns `live credentials are not allowed`. `bearer fixture-token` returns `secret value is not allowed` and is not echoed. `fixture-spot-order` returns `product is not supported` and is not stored. A later failing audit returns `release gate is blocked`. A Customer writes nothing. The check does not append a release audit. The module source does not read environment variables and does not call a paper order or the pre-trade gate. `pnpm health` returned `{"status":"ok","liveTrading":"OFF","liveOrdersLocked":true}`. Approval signature format, a 28-day paper count, and a 200-outcome count are NOT IN SOURCE. Decision 0076 records descendant-only delegation and does not change this lock.
